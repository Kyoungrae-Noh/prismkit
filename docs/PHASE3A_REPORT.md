# Phase 3A — 로컬 실사용 안정화

2026-10-21. 로컬 개발 전용. Cloudflare 운영 API·Access 정책·Secrets·배포 상태를 조회하거나 변경하지 않았으며 실제 네이버 API 호출, push, 운영 배포, DNS 변경은 수행하지 않았다.

## 구현

- `/keywords`에서 실제 키워드 입력과 명시적 LIVE 조회를 가장 먼저 제공한다. DEMO 탐색은 접힌 별도 예시 영역에 보존한다. LIVE/MANUAL/DEMO 출처와 확인 시각을 유지한다.
- 글감 목록 또는 편집창의 키워드 분석 링크로 키워드와 글감 ID를 전달한다. 후보 저장의 글감 연결을 자동 선택하며, 사라진 글감 연결은 저장 전에 차단한다. 페이지 왕복 중 조회 결과와 분류 입력은 메모리에 유지한다. 새로고침 전 미저장 LIVE 결과는 여전히 저장해야 한다.
- 문서 수 출처·확인 날짜·검색 범위를 수동 자료에 기록한다. 이전 자료에 검색 범위가 없으면 문서 수 필터를 통과시키지 않는다. LIVE 행에는 같은 키워드의 단일 유효 수동 근거만 연결하며 중복 근거는 임의 선택하지 않는다.
- `/backup`에서 네 저장소의 글감, 수동 키워드, 후보, 경쟁 자료, 캡처, 세 계정 이력과 Reviewman 연결을 통합 내보내기/복원한다.
- 기존 글감 CRUD, 개별 JSON, 경쟁·캡처·이력·중복 판단, Access JWT와 키 보호를 유지한다.

## API 예산 및 마이그레이션

- 기본 하루 30회, 최소 간격 10초, 성공 응답 캐시 5분. 한국시간 00:00 경계에서 새 날짜의 사용량을 적용한다. 별도 Cron이나 새 서비스는 필요 없다. 날짜 계산은 서버에서 하며 다음 요청/사용량 확인 시 영속화한다.
- 기존 SQLite Durable Object 이름, 클래스, 테이블, 바인딩을 유지한다. `budget.payload` JSON에 `version: 2`, `day`, `migrationDay`를 추가하는 지연 마이그레이션이다. Wrangler 설정 및 스키마 파괴 변경 없음.
- **기존 누적 데이터는 첫 접근 당일 사용량과 10회 상한을 유지**한다. 배포만으로 예산이 초기화된다고 가정하지 않는다. 다음 KST 날짜부터 하루 30회를 적용한다. 첫 접근이 배포 후 며칠 뒤라면 그 첫 접근일이 전환일이다.
- 401/403/429의 기존 `blocked` 상태는 마이그레이션·자정·재시작으로 해제하지 않는다. 자동 재시도나 차단 해제 API는 없다. 차단은 별도 관리자 점검이 필요하다.
- 예약을 동기 SQLite 쓰기로 외부 호출 전에 기록한다. 날짜가 바뀌어도 마지막 호출 시각과 진행 중 예약을 보존하여 자정 동시 호출로 간격 제한을 우회하지 못하게 한다. 실패한 외부 시도도 예산에 포함한다.
- `/api/searchad/usage`는 기존 JWT·호스트·Origin·요청 헤더 검증 뒤에만 접근 가능하다. 사용량 확인은 네이버를 호출하지 않는다. 응답에는 수치와 시각만 포함한다. 브라우저는 미확인 값 대신 `확인 불가`를 표시하며 자정 이후 오래된 사용량은 비운다.
- 로컬 Node 개발 API도 같은 날짜 기준으로 사용량을 계산하나 메모리 저장이므로 프로세스 재시작 시 초기화된다. 운영의 일관성은 Durable Object가 담당한다.
- 네이버 공식 FAQ는 속도 제한을 동적으로 적용하여 고정 수치를 보장하지 않는다고 설명한다. 따라서 30회/일은 네이버가 보장하는 허용량이 아닌 Prismkit의 자체 상한이다. 10초 간격을 유지하고 429를 받으면 일일 잔여량과 무관하게 차단한다. 계정별 실제 한도가 항상 이보다 높다고 추측하지 않는다.

근거: https://github.com/naver/searchad-apidoc/wiki/FAQ#q-api-호출-회수와-속도-제한이-있나요

## 전체 백업과 복원

- 백업 형식은 `format: prismkit-workspace`, `version: 1`. 기존 네 저장소 스키마는 그대로 검증한다. 키/토큰 저장소는 읽지 않으며 알 수 없는 필드의 가져오기는 거부한다. 자유 입력 메모와 캡처에는 사용자가 적은 개인정보가 포함될 수 있음을 안내한다. 서버 업로드 없음.
- 비교 화면은 자료별 개수와 동일/추가/같은 ID 변경/제거 개수를 보여준다. 전체 교체에 명시적으로 동의해야 복원이 가능하다. 병합 기능은 이번 통합 복원의 범위가 아니다.
- 중복 ID, 없는 글감 참조, 없는 후보 또는 다른 키워드에 연결된 경쟁 자료는 거부한다. 기존에 이미 끊어진 참조가 있는 백업도 임의 수정하지 않고 오류로 알린다.
- 네 키를 순차 덮어쓰는 대신 `prismkit.restored-workspace.v1`의 한 번의 `localStorage.setItem`으로 전체 스냅샷을 전환한다. 기존 네 키는 남기고 직전 유효 스냅샷을 자동 백업한다. 이후 CRUD도 동일 어댑터를 통해 복원된 자료에 기록된다.
- 직전 자동 백업은 별도 JSON으로 내려받을 수 있다. 다음 복원 시 직전 스냅샷이 갱신된다. 더 오래된 이력은 다운로드한 JSON으로 보관한다.
- 용량 초과 시 원래 데이터와 기존 통합 스냅샷을 변경하지 않는다. 자동 백업을 함께 보관할 여유 공간이 필요하므로 원본 파일이 작더라도 브라우저 여유 용량이 부족하면 복원이 거부될 수 있다.
- 미리보기 이후 자료가 바뀌면 재비교를 요구한다. 스키마와 참조는 쓰기 전에 검증하고 복원 후 재검사한다. 기존 키를 읽는 구버전 앱으로 되돌리면 복원 이후 자료를 인식하지 못하므로 코드 롤백 전 전체 JSON을 내려받아야 한다.

## 실험용 필터

| 프리셋 | 검색량 | 문서 수 |
| --- | --- | --- |
| 신규 블로그 실험 | 월 500 이상 | 300 이하 |
| 검색 수요 우선 | 월 3,000 이상 | 제한 없음 |
| 롱테일 발굴 | 월 0~2,999 | 1,000 이하 |
| 사용자 지정 | 직접 입력 | 직접 입력 |

검색량 빠른 설정: 500/1,000/3,000/5,000 이상. 문서 수: 300/500/1,000/5,000 이하. 프리셋에서는 미확인 검색량을 조건 충족으로 포함하지 않는다. 사용자 지정의 별도 미확인 검색량 표시 옵션은 검토용이며 조건을 충족했다는 뜻이 아니다. 문서 수 제한은 이 옵션과 무관하게 실제 수치와 근거가 있어야 통과한다. DEMO 문서 수는 통과하지 않는다.

원본 키워드를 삭제하지 않으며 필터를 해제하면 낮은 검색량 자료도 다시 보인다. 문서 수는 검색광고 경쟁도가 아니며 작은 문서 수나 필터 통과만으로 발행 판단을 상향하지 않는다. 네이버 자동 크롤링은 없다.

## 검증

최종 결과: **167건 전체 통과** — 프런트엔드 82, 로컬 서버 18, Edge 28, workerd 런타임 3, Chrome E2E 36. 타입 검사, 프로덕션 빌드, Worker dry-run/Pages Functions 빌드, 비밀정보 검사도 통과했다. 실제 네이버 응답·Access 인증 대신 모의 응답/JWT를 사용했다. 기존 테스트는 삭제하지 않았고, DEMO 영역 분리 및 저장 어댑터에 맞춰 선택자와 모의 저장소를 조정했다. 브라우저 테스트 산출물은 서버리스 빌드 산출물을 지우지 않도록 별도 하위 폴더로 분리했다.

- `npm run check`: 타입, 프런트엔드, 로컬 서버, Edge, 프로덕션 빌드.
- `WRANGLER_SEND_METRICS=false npm run test:runtime`: Worker dry-run, Pages Functions 빌드, SQLite 재시작/기존 payload 전환, JWT 라우팅.
- `npm run test:secrets`: Git 대상과 브라우저 번들에 로컬 인증값 부재, VITE_ 키 주입 차단.
- `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`: 1440/390/320px. 글감 연결, 필터, 후보 저장, 경쟁 화면, 다른 브라우저 백업 복원 및 재편집 포함.

## 배포 전 별도 작업

이번 단계는 배포하지 않았다. 운영 잔여 예산과 실제 연결 상태는 확인 불가이며 추측하지 않는다.

1. 별도 승인된 배포 작업에서 기존 Access/Secrets와 정상 배포 복구 지점을 확인한다.
2. 기존 브라우저 전체 자료를 백업하고 끊어진 참조를 검토한다. DO 예산/차단 상태의 복구 방안을 확인한다.
3. 같은 DO 이름·바인딩을 유지하고 Worker 변경과 Pages 변경을 함께 반영한다. Worker의 `usage` RPC가 없는 구버전과 섞이면 사용량은 확인 불가로 표시된다.
4. 전환일에는 기존 예산을 보존하는지, 다음 KST 날짜에는 새 한도가 적용되는지 확인한다. 차단 상태를 임의 해제하지 않는다.
5. 관리자 실제 로그인 후 화면과 승인된 최소 LIVE 조회를 별도로 검증한다. Phase 3B 및 운영 배포는 별도 명령을 기다린다.
